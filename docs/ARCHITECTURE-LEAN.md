# E-com.casa — Lean architecture

## Target

The application is a commerce runtime, not a crawler platform.

```text
GitHub (application code)
        |
        v
Vercel (Next.js)
        |
        v
PostgreSQL (Neon now, Supabase after cutover)
```

External integrations remain explicit and isolated: XPayments for payment processing, Resend for transactional email, and future carrier/tracking integrations.

## Catalogue source of truth

PostgreSQL is the authoritative mutable catalogue. The checked-in `data/catalog/generated-provider-*.json` snapshot is frozen transition/fallback data only; it is not regenerated by CI and must not be treated as a live supplier feed.

Normal product, price, stock, promotion or merchandising updates must become database mutations (future Admin/import tools), not Git commits.

## Retired architecture

The following responsibilities are intentionally removed from the deployed application repository:

- BigBuy integration and media enrichment
- Shopify supplier discovery/scanning
- recurring partner web scraping
- catalog research v1/v2 crawler engines
- generated supplier snapshot workflows that commit back to `main`
- runtime endpoints used only to trigger supplier imports/scans
- legacy Caddy/Python/non-Vercel runtime scaffold

One-shot external acquisition can still be implemented as an operator tool outside the commerce runtime when needed. Its output must be reviewed and written to PostgreSQL rather than committed as a generated production catalogue.

## Protected flows

Refactors must preserve these contracts:

1. catalogue / search / product pages
2. `/offers/[slug]` funnels and `ProductOffer`
3. cart and checkout server repricing
4. XPayments PaymentIntent creation and webhook reconciliation
5. orders, invoices, refunds and credit notes
6. fulfilment / tracking events
7. Resend transactional email
8. customer-facing concierge while enabled

## Future Admin / CRM

The next application layer should be an authenticated `/admin` surface over the same database. Planned domains:

- Dashboard: sales, AOV, conversion, paid/open orders
- Products: catalogue, variants, price, stock, media, SEO/compliance
- Offers: funnels, promotions, scheduling and audit
- Orders: payment/fulfilment lifecycle
- Customers / CRM: profiles, order history, notes, tags and lead state
- Payments: attempts, failures, refunds and reconciliation
- Logistics: shipments, tracking and incidents
- Marketing: campaigns, coupons, leads and abandoned checkout
- Analytics: UTM/source/funnel/product/margin attribution

Admin actions should write audited database records. They must not create Git commits or Vercel deployments.

## Deployment policy

A deployment is for application changes. Catalogue and operational data changes belong in PostgreSQL. Supplier sync jobs must never push generated data back to `main`.

Keep production on the current database while the lean branch is verified. Move to the new GitHub/Vercel first or in parallel, then perform the database cutover independently so rollback remains simple.
